# BUSINESS.md 业务知识治理

`BUSINESS.md` 保存不易从代码直接推导、但会影响实现和验收的业务规则、状态转换、特殊判断与历史决策。它不是 API 手册、普通工程规范或变更日志。

## 一、唯一 owner

- 根目录 `BUSINESS.md` 只做索引，不复制模块规则、不记录进度或审查状态。
- 详细业务知识放在实际拥有该行为的代码根目录，例如 `src/cli/BUSINESS.md`。
- 页面、交互流程和领域规则只有确实跨多个实现对象时，才提升到对应模块根目录。
- 一条规则只能有一个主要 owner；其他文档只链接，不重复维护两份同等权威的内容。
- 没有需要长期保存的知识时，不创建空文档，也不加入根索引。

## 二、内容要求

每份模块文档按实际需要记录：

- 范围和不涵盖的边界。
- 用户可观察的核心规则。
- 业务状态、生命周期和失败恢复。
- 特殊判断、禁止事项和历史决策。
- 能回到当前源码、测试或契约的相关代码入口。

文档只记录能够由代码、测试、API 契约或明确历史决策证明的行为；不把推测、前端状态或 mock 结果写成已确认保证。

## 三、迁移方式

1. 先盘点现有文档、测试、代码注释和实际行为。
2. 确认唯一 owner 和文档粒度，再依模板创建或更新模块 `BUSINESS.md`。
3. 把其他位置的重复业务结论改为链接，避免双份权威。
4. 校验相对链接、来源符号和业务边界。
5. 只有新 owner 完整且引用已更新后，才删除旧业务说明。

## 四、审查重点

- 规则是否由一个明确 owner 维护。
- 重要结论是否能追溯到当前源码、测试或契约。
- 是否把实现细节、API 字段或一次性进度误写成业务知识。
- 是否遗漏失败路径、状态转换或跨模块边界。
- 根索引是否只有一个有效入口，且没有空文档和失效链接。

CI 通过不能代替业务内容审查，业务文档也不能代替自动化测试。

## 五、反模式

- 在根索引复制完整业务规则。
- 为显得完整而创建没有规则的空文档。
- 同一规则在多个模块中重复维护。
- 记录开发状态、审查日期、PR 进度或测试数量。
- 把内部实现当作用户可观察业务事实。
- 迁移后保留多份同等权威的旧文档。
